# 图表的排版

模型画出的坐标是一份草稿：它想说「这几个方框是一行」「这两个应该上下对齐」，只是手抖了几像素。排版要做的，是读懂这份草稿，再把几何重新算一遍。

## 整理：把草稿读成意图

整理（tidy）在每张新图上画布前运行，纯字符串处理 XML，不依赖 DOM，所以浏览器和测试里跑出来完全一样。它分五步：

1. **分行**：在每个容器里把方框按纵向位置归成行，每行统一一条中线；宽度本来就接近的，统一成一个宽度。
2. **减交叉**：在一行之内调换方框的顺序，只要这样能减少连线交叉和折弯。
3. **对齐**：先把最满的一行均匀排开，再让其他方框对准它们所连接的方框，同时保持顺序和最小间距。
4. **吸附**：坐标吸附到 10px 网格；容器装不下自己那一行时，把容器撑大。
5. **布线**：两端已经对齐的连线拉直，否则只在两行之间的空隙里拐一次。

它没有动过的每个单元格，都保持模型写下的原样，一个字节也不改。

> [!WHY]
> 只整理**分层、正交布线**的图。思维导图、环形图、自由散点没有「行」可以恢复，硬猜一个行结构只会把它们弄坏，所以这些图原样返回。宁可不整理，也不要整理错。

## ELK：更彻底的重排

整理只做微调。有些图本身的层次就乱，这时需要真正的布局算法。CanvasAnvil 用 [ELK](https://eclipse.dev/elk/) 的 **layered**（分层）算法，并且：

- 把模型原来的顺序和位置作为偏好传给 ELK，让它尽量沿用；
- 按需加载——ELK 大约 1.5MB，只在需要时才下载，并且在新图已经上屏之后于后台运行。

我们也试过 ELK 的 mrtree、radial、stress 等算法。它们在评测集上要么打乱了模型的意图，要么分数不如分层算法，最终都没有采用。

## 选哪一份：一次比较

```diagram
diagram-arrange
```

每张图有三个候选：模型原稿、整理稿、ELK 稿。它们都交给 **layout-lint** 打分，分数列在对话里，由你来挑：

- **layout-lint** 给任何 draw.io 图打 0–100 分。硬性问题包括：形状重叠、跑出所属容器、容器互相重叠、连线穿过形状、文字装不下、连线缺端点；软性指标包括交叉、折弯，以及「差一点就对齐」的近似错位。
- 新图先以整理稿上屏（整理稿分数更低时用原稿）；ELK 在后台算完后只列出分数，**不会自动换上**。
- 点一个候选，画布就换成它；选好后点 **确定**，后面的修改都在这张图上进行。

> [!WHY]
> 为什么不自动挑？分数高不等于保住了你的意思。ELK 会让每一层自己排齐，却常常打散跨层的列：在评测图上，它重排后平均只剩约 30% 的原有对齐，可这些图在 layout-lint 上照样拿高分。用门槛去猜「改没改坏」，结果是 ELK 几乎从不被选上；交给你看一眼再定，更直接。

## 可以随时看回原稿

每次整理或重排都会记下所有候选。确定之前，对话里的「布局矫正」一步可以在模型原图、整理稿和 ELK 稿之间随意切换。

## 局部修改时

一次局部修改只触及几个单元格。这时整理只重新排布包含这些单元格的行，其余部分保持不动——你刚亲手调好的位置不会因为改了一个字而跑掉。
