# 图表的对话管线

一条消息从输入框出发，到一张图落在画布上，中间经过 `/api/chat` 里的几道工序。每一道都只做一件事，放在 `server/chat/` 下各自的文件里。

## 判断意图：改一处，还是重画

`intent.ts` 判断你是在调整某个节点，还是要一张新图。前者必须保留现有 XML，后者可以替换。

> [!WHY]
> 判断错了的代价很不对称：把局部修改当成重画，会悄悄丢掉你的整张图；把重画当成局部修改，最多是多说一句话。所以只要你明确说了「重新画」之类的话，它永远优先；其余情况下倾向于局部修改。

## 读材料：把文档压进上下文

上传的 PDF 和 Word 在服务端解析（`files.ts`）。太长的文档由 `summarize.ts` 压缩：短文档每块摘要一次再合并，长文档反复折叠，直到剩下的摘要足够少。

> [!WHY]
> 如果模型拒绝摘要，或者反过来要求你提供更多材料，就重试一次；还不行，就换成机械抽取的原文片段。一份糟糕的摘要会悄无声息地毒害后面画出的图，所以它绝不能进入提示词。

## 修历史：只给模型看现在的图

之前每一轮的工具调用里都带着整张图的 XML。如果原样送回，每次请求都会被这些旧图撑满。`messages.ts` 把历史中的 XML 换成占位符，只保留当前这张图作为唯一的事实来源。它也顺手修正有些服务商把工具参数流式输出成字符串的问题。

## 按需加载图形库

draw.io 有大量专用图形：AWS、Azure、Kubernetes、网络设备、UML……全部塞进系统提示词既贵又分散注意力。模型需要时，会通过工具调用去取对应图形库的说明（`shape-library.ts`），用多少取多少。

## 深度思考：先画一张草图

打开深度思考时，`deep-thinking.ts` 先让图片模型把这张图画出来，再把图片交给文本模型作为布局参考。配置了调试目录时，草图会保存到磁盘。

> [!WHY]
> 布局糟糕时，问题可能出在「想」上，也可能出在「把想法翻译成 XML」上。唯一分清两者的办法，是看看图片模型实际画了什么。

## 流式返回与上画布

模型以工具调用的形式流式写出 XML，前端边收边显示进度。完整的 XML 到达后，先经过 [排版](/docs/diagram-layout) 的快速整理，再交给 draw.io 显示；生成过程中，对话和图每 3 秒保存一次。
